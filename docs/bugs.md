| 2026-11-10 | "on restore there seems to be some frozen parts of the terminal" | Build 1121 (`eed7218c`) held size reports to the session while the scene was inactive, but the page still reflowed its grid for the keyboard hiding and returning. The session (mosh, tmux) kept drawing for the old layout, so output landed on the wrong rows, and since the size it finally heard was the one it already had, nothing repainted. Traced in code, not reproduced on a device. Fix: the page holds its grid while the scene is inactive (`term_holdResize`) and takes the settled size once, after activation. | `node tools/termjs-tests/resizehold.test.js`; `ResizeRules.settles` in FleetCore tests; device check MANUAL-TESTS Feature I |
| 2026-11-10 | Local `blink>` shell: hiding the keyboard on a full screen wipes the lines under the prompt (found in the simulator while checking the row above; older than that fix) | The local prompt remembers the screen row it started on. A height change moves rows between screen and scrollback and the cursor with them, but the remembered row stayed, so the prompt redrew on the old row and erased everything below it. Fix: the start row moves as far as the cursor did (`blink_promptStartRow`). | `node tools/termjs-tests/resizehold.test.js` (prompt row checks); simulator keyboard hide and show on a full screen |
| 2026-11-10 | "there are still weird loading artifacts when i load back into tmux on blink" (on build 1124) | Follow-on from the first row's fix, reproduced in the simulator with mosh + tmux and a screen recording. While the grid was held, the keyboard hiding made the view taller and the scroll view pulled its offset back to fit; that move was reported to the page, which then drew from the top of its buffer (old rows from tmux's alternate-screen scrollback, no status line) for about 0.8 s after coming back, until the hold ended. Fix: while held, the scroll view's own refitting is not reported, the page's moves still are, and the position is restored when the hold ends (`WKWebViewGesturesInteraction.setResizeHeld`). | `ScrollRules.reportsScroll` in FleetCore tests; simulator recording of leave and return with mosh + tmux (start `mosh-server new -p <free port> -- tmux -L blinkrepro new -A -s repro <ticker>`, connect with `mosh -k <key> -p <port> 127.0.0.1`, record with `simctl io recordVideo`, check the frames right after return show the status line) |
| 2026-11-12 | "when i come back to the app its blank or sometimes unresponsive" (build 1126) | Build 1126 started handling the terminal page's process being killed by iOS (it reloads the page), but the reload path skipped what the normal "page is ready" path does. Three gaps, each reproduced in the simulator by killing the page process: (1) coming back to the app takes the keyboard only if the page is ready, otherwise it waits for a ready signal the reload path never sent, so the tab took no typing; (2) the same wait applies to resuming a suspended session (traced in code, not reproduced); (3) a local `blink>` prompt lives in the page and was not shown again, so the tab came back blank. Also found: a restored tab whose saved session is missing stayed blank for good. Fix: after a reload the tab resumes or starts its session, takes the keyboard and shows the local prompt again (`TermController.deviceDidRecover`, `TermDevice.viewDidRecover`); a tab with nothing to restore gets a shell; a session is left marked suspended while the phone is locked so its state is read after unlock. | `tools/sim-page-kill.sh` (fg, bg, bg 330, each followed by `type`): screen back, typing lands, Blink pid unchanged |
| 2026-11-12 | "its crashed theee times today" (build 1126) | Not root-caused: App Store Connect holds no crash reports for 1126 and the phone's logs were out of reach, and no crash reproduced in the simulator. Likeliest cause, from the host's hook log: every agent turn woke the app in the background (the "finished" push carried `content-available`, and the lock-screen activity was started and ended by push on every turn, 14 starts on 2026-11-12), and each wake reloaded dead terminal pages in the background, one new page process per tab, which is memory iOS kills a background app for. A kill like that looks like a crash: the app starts over. Fix: quiet pushes no longer wake the app; the activity starts only after 45 s of running (at once for "needs input") and ends after 120 s idle; a page that dies in the background is reloaded when the app comes forward, not before. If it still happens on 1127, get the log from the phone (Settings > Privacy & Security > Analytics & Improvements > Analytics Data, `Blink-…ips` or `JetsamEvent-…ips`) before changing anything else. | `scripts/fleet/test_blink_fleet.py` (`test_activity_waits_before_starting_and_ending`, quiet payload has no `content-available`); `tools/sim-page-kill.sh bg` prints no page process while in the background |
